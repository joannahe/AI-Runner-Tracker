# Athlete questions and first-run setup

This is an English-first product specification for the reusable running ontology. The Chinese questions are example UI translations. Replace “my” with a selected athlete only when the speaker has permission to view that athlete's records. These are **question and answer contracts**, not assertions about the included owner's health.

## How an answer should work

The athlete should be able to ask an ordinary, underspecified question. The Agent resolves the athlete, local date range, source and applicable rule version from the ontology and saved preferences. It then chooses relevant observations and comparisons rather than making the athlete name metrics or thresholds. Show the observation, its personal baseline or provider range, valid-day coverage, the triggered review rule, and any missing evidence. Separate a device label from this project's configurable review signal. A review signal is not a diagnosis. Suggest a plan change for athlete approval; do not silently change an approved plan or a provider schedule. DOSI currently exposes source data and concept mappings; an Agent or future evaluator must calculate and save new reviews.

Ask a follow-up only when a missing choice changes the answer materially: for example, the athlete has several active goals and did not identify one, or a question asks **which scheduled workout** to change but no schedule is available. If a documented default resolves an ambiguity, use it and state the interpretation in the answer. Do not turn an open-ended question into a request for the user to supply the formula.

**Proposed UI default:** interpret “recently” as the last **seven completed local days** for a recovery review. This phrase-to-date behavior is not implemented yet. Long sleep-quality baselines use the **preceding 42 wake dates** and do not include the current day. Weekly mileage comparisons use the **last two completed, consecutive Monday–Sunday weeks**. Display the resolved dates and let the athlete change them.

## Reusable question catalog

| User question (English / 中文) | Ontology path and comparison | Answer and present status |
| --- | --- | --- |
| **Am I recovering okay lately?** / 我最近恢复得怎么样？ | `Athlete → DailyTrainingLoad / SleepObservation / RestingHeartRate / OvernightHRV → RecoveryState → InferredState`. Review dated provider load ratio, sleep and resting-HR trends; distinguish the two-signal composite from the one-signal `CompromisedRecovery` review. | Give resolved dates, values, personal baselines, source and missing days. Say “review suggested” rather than “you are fatigued.” **Queryable inputs; no automatic personal `RecoveryState` evaluator.** |
| **Have I been training too hard?** / 我最近是不是练得太狠了？ | `DailyTrainingLoad.load_ratio > 1.5` by default, or the athlete's effective override; review other available recovery signals separately. | List dates and ratios; label `OvertrainingRisk` as a high-load *review flag*, not overtraining syndrome. **Agent rule only.** |
| **When was I well rested, and when was I not?** / 我最近哪天休息得好，哪天不太好？ | `RecoveryState` considers COROS recovery estimate, dated sleep, RHR and personal HRV range. Compare each source separately; no universal “good recovery” score is defined. | Describe favorable and concerning observations side by side, with coverage. Avoid claiming a low score proves poor health. **Source data queryable; composite classification not implemented.** |
| **Have I been sleeping enough?** / 我最近睡得够吗？ | `SleepObservation.main_sleep_min` vs valid observations in the preceding 42 wake dates; flag outside ±10% with at least 28 valid prior days. | List wake dates, minutes, baseline and percentage difference. A longer night is not automatically poor sleep. This model does not decide a universal sufficient duration. **Agent rule only.** |
| **Was my sleep any good this week?** / 我这周睡得好吗？ | `SleepObservation.sleep_score < 90%` of the mean of valid scores in the preceding 42 wake dates; at least 28 valid scores. | Show source score, baseline, date and rule version. Keep sleep score distinct from sleep duration. **Agent rule only.** |
| **Does my heart rate suggest I need a break?** / 我的心率是不是说明该休息了？ | For the same local date, `RestingHeartRate.rhr_bpm > mean(valid observations in preceding 7 local dates) + 5 bpm`; at least five valid prior days. A separate rule reviews a >10% rise. | Show both the daily value and baseline; check other recovery evidence and do not attribute a rise to training alone. **Agent rule only.** |
| **Is my HRV looking normal?** / 我的 HRV 最近正常吗？ | `OvernightHRV.hrv_avg_ms < normal_low_ms` for the same wake date. Do not use a population cutoff. | List dated COROS value and personal lower bound; report missing ranges separately. **Queryable with current personal data.** |
| **Should I take it easy tomorrow?** / 我明天要不要练轻松一点？ | `CompromisedRecovery → Recommendation → PlannedAction`. A valid RHR, HRV or sleep-score signal on the workout morning requests review. A same-day uncompleted Tempo/VO₂ Max action would be a candidate for an Active Recovery or Rest **draft**. | Resolve “tomorrow” in the athlete's timezone. Today's evidence supports only a preliminary suggestion; recheck tomorrow morning before a same-day review. If no dated structured plan exists, say “I cannot identify a specific scheduled workout.” **No automatic evaluator, workout subtype, draft generator or notifier yet.** |
| **Is my mileage going up too fast?** / 我的跑量是不是涨得太快了？ | `RunningObservation → WeeklyRunningDistance → HighMileageGrowthWeek`. DOSI queries an Ossie `derived_by` subtype for default growth `> 10%`; the mapped warehouse view compares all measured running, including hybrid run segments, in two consecutive verified complete weeks. | Show both week ranges, km and percentage. Missing coverage produces no classified week; explain that absence of a match is not proof of normal growth. The 10% condition is a planning heuristic, not proof that a smaller increase is safe. **DOSI-executable default classification; Agent reviews the plan.** |
| **Am I doing too much hard running?** / 我是不是高强度跑太多了？ | `SourceActivity.training_focus → TrainingSession → PolarizedHighIntensityReview`. Count deduplicated completed running sessions tagged high, with low/moderate shown separately. Default review if high-count share `> 20%` in a completed week. | Report session counts and unknown labels. Do not present this as time spent in heart-rate zones. **Agent rule only; complete focus coverage required.** |
| **Can I train hard again after my race?** / 比完赛我能继续练强度吗？ | `RaceEvent` is a completed running `TrainingSession` subtype. Resolve its race format or one canonical watch activity distance, the athlete's effective easy/rest-window setting and the next high-intensity action. | Show the race date, selected distance source, configured window and affected action. If distance or the setting is missing, ask for that input; do not invent a universal waiting period. **Agent review rule; no automatic block.** |
| **Does my plan give me enough recovery after a race?** / 我赛后的安排恢复够吗？ | Use the same race and plan evidence; check every dated high-intensity action inside the configured window, then review available recovery observations separately. | Distinguish a schedule-rule conflict from evidence about actual recovery. Suggest an easy/rest draft for approval; keep an approved plan intact. **Requires a usable watch or race-format distance and an athlete setting.** |
| **Is next week's training spaced well?** / 下周训练安排合理吗？ | `Athlete → ActionPlan(version) → PlannedAction → HardEasySequenceReview`. Order actions by local date; inspect consecutive high-intensity actions and any explicit easy run or rest day between them. | Identify the two dated actions and proposed adjustment. A blank day is unknown, not an assumed rest day. **Agent review rule; current plan intensity field is not mapped.** |
| **Am I stacking hard workouts?** / 我是不是把强度课排得太密了？ | Same plan path; use structured planned intensity rather than the free-text workout title or a completed activity's COROS focus. | Flag back-to-back high-intensity actions when evidence is complete. If intensity is absent, say which actions need classification before giving a pass or warning. **Agent review rule.** |
| **Should I move tomorrow's interval session?** / 明天的间歇课要改吗？ | Check both `PostRaceRecoveryReview` and `HardEasySequenceReview` for tomorrow's local date, then inspect biometric recovery signals separately. | Say which check applies, cite the prior race or hard session and the plan version, and offer a draft change for athlete approval. Missing race policy or plan intensity yields an explicit evidence gap. **No automatic plan edit.** |
| **How far am I from my goal?** / 我离目标还有多远？ | `Athlete → Goal(version) → GoalCriterion → GoalProgressAssessment / GoalProgressEvidence`. Resolve each current criterion by its own metric, unit, period and comparison direction. | For a 10K time goal, use a comparable same-distance official result; for a weekly run-days goal, show observed vs target days. A half-marathon time gap needs a comparable result or clearly labeled prediction. **Personal goal and criterion must be entered; ask which goal only if several active goals make the answer ambiguous.** |
| **Am I on track?** / 我现在算是在按计划进步吗？ | Resolve the selected active goal and its criteria; `RecoveryState` and `Capability` are context, not substitutes for target evidence. | Show achieved/on-track/needs-review/insufficient-evidence per criterion, plus the review date and method. Do not invent one overall goal-progress percentage. **Requires saved goal and dated assessments.** |
| **Am I becoming a better runner?** / 我的跑步水平有进步吗？ | `Capability → MetricEvidence → FitnessAssessment / RunningObservation / PaceZone / TrainingSession`. Compare device estimates and comparable runs across dates. | Describe supported pace, HR, race or zone trends, including comparability limits. Do not infer improvement from a single zone snapshot or cadence alone. **Queryable inputs; personal capability assessment evaluator not implemented.** |

## Acceptance scenarios for the two plan rules

These are fictional test inputs, not findings about the sample athlete. Set an explicit recovery policy for the test athlete; the production default is unset.

| Test input | Question to ask | Expected Agent behavior |
| --- | --- | --- |
| Verified 10 km road race on Sunday; test policy is 0.2 easy/rest days per km, giving a two-day window; high-intensity action on Monday | “Can I do Monday's workout?” | Raise `PostRaceRecoveryReview`; show race date, verified 10 km, configured 0.2 and calculated two days. Suggest an easy/rest draft for approval. Do not change the approved plan. |
| Same race and policy; first high-intensity action on Wednesday | “Is Wednesday's workout okay after the race?” | No post-race *window* conflict. Check other recovery evidence and hard/easy sequencing separately; do not claim medical readiness. |
| Running race without a usable canonical watch or race-format distance, or no athlete recovery setting | “Have I rested enough after the race?” | Return insufficient evidence for the window and identify the missing item. Do not activate the optional one-day-per-mile example as a universal rule. |
| High-intensity planned Monday and Tuesday, with both intensities recorded | “Is my week balanced?” | Raise `HardEasySequenceReview` for Tuesday, cite both dated actions and the plan version, and offer a draft move or downgrade. |
| High-intensity Monday, explicit rest Tuesday, high-intensity Wednesday | “Are my hard sessions too close?” | No hard/easy sequence flag from these actions. Do not generalize this to a claim that the whole plan is safe. |
| High-intensity Monday and Thursday; Tuesday and Wednesday have no plan entries | “Did I leave enough easy time?” | Report unknown intervening recovery; ask whether those dates were rest/easy days. Do not silently count them as rest. |
| Two planned runs with only `action_kind=run` and free-text titles | “Are these two hard days?” | Explain that planned intensity is unavailable. Do not infer high intensity from titles or completed COROS focus labels. |
| A rule conflicts with an approved plan | “Please fix my plan.” | Show a proposed new plan version and request approval; preserve the approved version and do not write to the wearable provider. |

## First-run information to request

The onboarding UI should ask for the smallest set needed for the user's intended questions. “Required” below means required for that function, not mandatory for every account.

| Information | When needed | Where it maps / why |
| --- | --- | --- |
| **Athlete identity and consent** | Required to import any wearable data. | Create a stable `athlete_id`; connect only the authorized wearable account. Keep provider credentials and raw tokens out of the shareable dataset. For multiple athletes, require an explicit active-athlete selection and access check. |
| **Local timezone** | Required for daily recovery and completed-week comparisons. | `Athlete.timezone_name`; aligns activity dates, wake dates, local HR/load dates, and Monday–Sunday weeks. Do not infer it from the device location. |
| **Watch source, permissions, and import range** | Required to import. | COROS or Garmin connection and requested data categories: activities, daily load, sleep, resting HR, HRV, zones and available fitness estimates. Show what the connector actually returned; do not assume every provider supplies every category or full history. |
| **Source-data review** | Required before trusting trend questions. | Confirm source ownership, duplicate activities, official race vs watch timing, measured vs reference distance, units, and import coverage. Missing readings remain missing, not zero. |
| **Goal, target and date** | Required for goal-gap and plan questions. Optional for descriptive dashboard use. | Create versioned `Goal` and one or more `GoalCriterion` rows: goal type, target distance/time or frequency/sleep outcome, target date, unit, comparison direction, and review window. A finish-only race goal need not have a target time. Multiple goals may coexist. |
| **Planned training and approval preference** | Required to name a particular day or workout for a suggested reduction. | `ActionPlan` and dated `PlannedAction`, including workout subtype and completion state. The current table has generic `action_kind`; structured Tempo/VO₂ Max recognition and provider plan import remain to be built. Ask the athlete to approve any draft change. |
| **Race recovery preference and watch distance** | Required for a dated post-race high-intensity review. | Use a completed running race and a known race-format distance or one canonical watch activity distance. Ask for an athlete-configured easy/rest-window setting with effective date. There is no active universal days-per-mile default; the setting and evaluator are not yet implemented. |
| **Personal rule thresholds** | Optional; defaults apply only after being shown to the athlete. | Defaults: COROS load ratio `>1.5`, completed-week mileage growth `>10%`, RHR `>5 bpm` above the prior-seven-day mean, sleep score `<90%` of the prior-42-day mean, high-focus session share `>20%`. Record effective value, date and rule version when a future evaluator runs; per-athlete override storage is not implemented. |
| **Proactive coaching preference** | Required before sending any recurring reminder. Optional for on-demand questions. | Ask for daily and/or weekly reviews, morning time, timezone, reminder channel and whether health details may appear in messages. These preferences, the scheduler and the notification log are not yet implemented; see `TRAINING_COACH_AGENT.md`. |
| **Age or birth date, gender, other health context** | Optional for this ontology's basic trend comparisons; ask only when a chosen reference or goal needs it. | Do not infer demographic norms or medical risk from missing profile details. The current generic `athlete` table does not persist all profile fields from the source warehouse. Subjective fatigue input is intentionally excluded. |
| **Privacy and sharing choice** | Required before exporting or publishing a personal dataset. | The owner's sample is shared by explicit choice. A new athlete's health data must not be included in a public seed or static dashboard merely because they imported it locally. |

## Current implementation boundary

The included personal snapshot and DOSI-compatible DuckDB overlay contain real observations, including 166 dated HRV assessments. The overlay also contains fictional goals, plans and recovery reviews for demo athletes; it contains **no personal goal, dated personal plan, or computed personal `RecoveryState` review**. `fitness_ontology.yaml` and `RECOVERY_RULES.md` express the quantitative rules for Agent review. DOSI maps the concepts and metrics but does not execute the rules, generate plan drafts or send reminders. Do not demo those outcomes as completed product behavior until an evaluator, evidence persistence and human approval flow exist.
